# cap — Meeting Capture + Real-time Analysis

미팅 중 화면 스크린샷과 실시간 번역 텍스트를 **저장하고 즉시 분석**하는 스킬. 이 플러그인의 핵심.

## 사용자가 무엇을 하려는지

외국어(주로 일본어) 미팅에 참여 중이고, 실시간 번역 앱을 통해 텍스트로 번역된 발화를 약간의 딜레이로 받는다. 발표 화면의 자료가 어렵고 번역기는 전문 용어를 자주 오인한다. 사용자에게 가장 가치 있는 것은:

1. **화면과 발화를 페어로 보존** (나중에 다시 볼 수 있도록)
2. **매 캡처마다 즉각적인 도움** — 방금 저장한 내용에 대한 짧은 분석을 바로 받는 것
   - "방금 발화의 핵심이 뭐였지?"
   - "번역기가 이상하게 번역한 부분은?"
   - "처음 보는 용어는 뭐고, 뜻은?"
   - "이전 흐름과 어떻게 연결되지?"

**핵심 통찰**: 미팅 후 전체 분석은 사용자가 직접 텍스트를 다시 읽어도 가능하다. 진짜 가치는 **미팅 중 그 순간** 흐름을 놓치지 않게 도와주는 것이다.

**목표**: 캡처와 동시에 짧고 즉각적인 분석을 제공하여 사용자가 미팅 흐름을 즉시 따라잡게 한다. 저장 + 분석 합쳐서 **5~7줄 이내**의 응답을 유지한다.

## 동작 모드

사용자 메시지의 내용으로 모드를 자동 판별한다.

### 모드 1: 새 미팅 시작 — `/cap new {meeting-name}`

예: `/cap new mitsui-q2-review`

1. `~/meetings/{YYYY-MM-DD}-{slug}/` 디렉토리 생성
   - slug = meeting-name을 소문자/하이픈으로 정규화 (한글은 그대로)
   - 같은 날 같은 이름이 이미 있으면 `-2`, `-3` 접미사
2. 그 안에 `images/` 서브디렉토리 생성
3. `notes.md` 초기화:
   ```markdown
   # 미팅 — {meeting-name}

   - 날짜: {YYYY-MM-DD}
   - 시작: {HH:MM}
   ```
4. `context.md`를 템플릿 기반으로 초기화 (비어 있는 상태로 생성하여 사용자가 채울 수 있도록):
   ```markdown
   # Context — {meeting-name}

   > 이 파일은 선택사항이지만, 채워두면 분석(meeting-review) 품질이 크게 향상됩니다.
   > 언제든 `/cap context ...` 로 추가하거나 직접 편집 가능합니다.

   ## 미팅 목적

   ## 참가자 (이름 / 역할)

   ## 프로젝트 배경

   ## 본인 역할 / 알고 싶은 것

   ## 관련 자료 (링크, 파일)
   ```
5. `~/meetings/.current`에 새 미팅 폴더의 절대 경로를 한 줄로 기록 (활성 미팅 추적)
6. **한 줄로 확인 + context 안내 한 줄**:
   ```
   📁 새 미팅 시작 — {경로}
   💡 배경 정보 있으면 `/cap context ...` 또는 자연어로 알려주세요 (선택)
   ```

### 모드 2: 새 슬라이드 캡처 — 메시지에 이미지가 있을 때

이미지 **유무**로만 판별. 텍스트가 같이 있어도 OK, 없어도 OK.

#### 저장 단계

1. `~/meetings/.current` 읽어 활성 미팅 폴더 찾기
   - 없으면: `⚠️ 활성 미팅 없음. /cap new {이름}으로 먼저 시작하세요.` 하고 중단
2. 활성 미팅의 `images/`를 스캔해서 다음 슬라이드 번호 결정 (`slide-01`, `slide-02`, …)
   - **항상 디렉토리 스캔 기반**. notes.md 파싱 의존 금지
3. 첨부 이미지를 `images/slide-{NN}.png`로 저장
   - Claude Code가 이미지 경로를 노출하는 방식:
     a) 임시 파일 경로(예: `/var/folders/.../clipboard-*.png`)가 보이면 → `cp`로 복사
     b) 경로가 불분명하면 → 추측 가능한 가장 합리적인 경로로 시도 후 실패 시 보고
4. `notes.md` 끝에 새 섹션 append:
   ```markdown

   ## 슬라이드 {NN} ({HH:MM})
   ![](images/slide-{NN}.png)

   ```
5. **메시지에 텍스트가 같이 있다면** → 그 텍스트를 모드 3 저장 로직으로 첫 발화로 즉시 추가

#### 분석 단계 (중요 — 모드 2에서 항상 수행)

저장 후 즉시 짧은 분석을 출력한다 ([실시간 분석 형식](#실시간-분석-형식) 참고).

이미지 캡처는 시각 정보가 새로 들어왔으므로 분석에 다음을 포함:
- 📊 **슬라이드 요약**: 새 화면이 무엇을 보여주는지 한 줄 (Read 도구로 이미지를 빠르게 분석)
- 💭 **요지** (텍스트 있을 시): 발화의 핵심
- 🆕 **새 용어**: 처음 등장한 일본어/약어
- ⚠️ **번역 의심**: 번역기가 오인한 듯한 부분

### 모드 3: 기존 슬라이드에 텍스트 추가 — 이미지 없이 텍스트만

#### 저장 단계

1. `~/meetings/.current` 읽어 활성 미팅 찾기 (없으면 모드 2와 동일하게 안내)
2. `notes.md`를 읽어 가장 마지막 `## 슬라이드` 섹션 위치 찾기
3. 그 섹션 끝에 발화 블록 append:
   ```markdown

   ### [{HH:MM}] 발화

   > {사용자가 보낸 텍스트 — 원문 그대로 preserve}
   ```
   - 사용자 텍스트가 여러 문단이면 각 줄 앞에 `> ` 를 붙여 blockquote로 보존
4. 만약 아직 슬라이드가 하나도 없다면 (`## 슬라이드` 섹션 없음): notes.md에 `## 메모 (슬라이드 없음)` 섹션을 만들고 거기에 추가

#### 분석 단계 (중요 — 모드 3에서 항상 수행)

저장 후 즉시 짧은 분석을 출력한다.

텍스트만 캡처는 발화 내용에 집중:
- 💭 **요지**: 방금 발화의 핵심 (한 줄)
- 🆕 **새 용어**: 처음 등장한 용어 (있으면)
- ⚠️ **번역 의심**: 번역기 오인 의심 (있으면)
- 🔗 **맥락 연결**: 같은 슬라이드 내 이전 발화와 어떻게 이어지는지 (필요 시)

### 모드 4: 배경 정보 저장 — `/cap context {내용}` 또는 자연어 감지

**명시적 형태**: `/cap context 이 미팅은 일본 Payroll 팀 기술 리뷰고, 나는 한국 쪽 PM이야`

**자연어 감지**: 사용자가 "이 미팅은 ~에 대한 거야", "참가자는 A, B, C야", "배경: ~" 같은 문장을 보내면 **현재 활성 미팅의 context**로 판단.
- 판단이 애매하면 물어본다: "이걸 context.md에 저장할까요?"

동작:
1. `~/meetings/.current` 읽어 활성 미팅 찾기
2. 활성 미팅의 `context.md` 읽기
3. 적절한 섹션에 사용자 내용 통합:
   - 내용이 "참가자"에 대한 것 → `## 참가자` 섹션 아래 추가
   - 내용이 "목적/배경"에 대한 것 → `## 미팅 목적` 또는 `## 프로젝트 배경`
   - 섹션 판별이 어려우면 `## 기타 메모` 섹션에 append
4. 한 줄 확인: `📋 context 저장됨`

## 시간/날짜 표기

- 시각: `date "+%H:%M"` (24시간제, 로컬 시간)
- 날짜: `date "+%Y-%m-%d"`
- 모든 타임스탬프는 사용자의 macOS 로컬 시간 기준

## 활성 미팅 상태 추적

`~/meetings/.current` 파일이 단일 진실 공급원:

- 내용: 활성 미팅 폴더의 절대 경로 한 줄
- 새 미팅을 만들 때마다 덮어쓴다
- 사용자가 명시적으로 "미팅 끝" 같은 말을 하면 비워도 좋지만, 강제는 아님

## 실시간 분석 형식

저장 직후 짧은 분석을 출력한다. **가독성이 최우선**. 사용자는 미팅 중에 이 출력을 힐끗 보고 이해할 수 있어야 한다.

### 표준 출력 형식 (수직 레이아웃, 불릿 사용)

```
📸 슬라이드 {NN} + 발화 ({HH:MM})

📊 슬라이드
   • {한 줄 요약}
   • {보조 정보 — 선택}

💭 요지
   • {핵심 1}
   • {핵심 2}
   • {핵심 3 — 선택}

🆕 새 용어 (top 3)
   • {용어1} — {짧은 정의}
   • {용어2} — {짧은 정의}
   • {용어3} — {짧은 정의}

⚠️ 번역 오인 (top 3)
   • "{이상한 번역}" → {보정}
   • "{이상한 번역}" → {보정}
   • "{이상한 번역}" → {보정}

🔗 맥락
   • {이전 흐름과의 연결 한 줄}
   • {미결/후속 액션 — 선택}
```

### 항목별 규칙 (엄격)

**공통 규칙**:
- 각 섹션은 **이모지+라벨 한 줄** 다음 **들여쓰기 불릿**으로 내용
- 각 불릿은 **한 줄 — 최대 ~30자**. 길면 짜르거나 쪼갬
- **섹션 간 빈 줄 1개**로 시각 구분
- 해당 사항 없는 섹션은 **통째로 생략** (라벨도 출력 안 함)

**📊 슬라이드** (이미지 캡처 시만)
- 1~2개 불릿. 이미지가 보여주는 것 핵심만.
- ❌ 긴 나열 ("컬럼: A/B/C/D/E/F/G") 금지 — 핵심 패턴만 ("종별 × 정기권 매트릭스")

**💭 요지**
- **최대 3개 불릿**
- 각 불릿은 한 생각만 담음
- 발화자 인용 시: `• [발화자]: "짧은 인용"` 형식

**🆕 새 용어**
- **최대 3개** (그 이상 보이면 가장 중요한 3개만)
- 포맷: `• {원어} — {10~15자 정의}`
- 이미 글로서리에 있는 용어는 표시 안 함 (grep으로 확인)
- 한 줄에 여러 용어 나열 금지 (반드시 불릿 분리)

**⚠️ 번역 오인**
- **최대 3개**
- 포맷: `• "{이상한}" → {보정}` — 화살표 정렬
- **가장 가치 있는 섹션**이므로 발견하면 우선 노출
- 원문(일본어/중국어) 명시는 선택 — 너무 길면 생략

**🔗 맥락**
- **최대 2개 불릿**
- 이전 발화/슬라이드와의 연결 + 미결 후속 액션
- 너무 평범한 이어짐 ("앞 내용 부연")은 생략

### 분석 길이 원칙

- **전체 약 15~25줄** (섹션 라벨 + 빈 줄 + 불릿 포함)
- 짧은 불릿 × 많은 줄이 긴 문장 × 적은 줄보다 **훨씬 읽기 쉬움**
- 해당 항목 없으면 생략 — 빈 라인이나 "없음" 라벨 금지
- 분석할 게 진짜 없으면 (모드 1, 모드 4) 저장 확인만 1~2줄

### ❌ 절대 피할 것

```
❌ 나쁜 예 (벽):
📊 슬라이드: P3 화면 "継続支給の確認" 테스트 환경(2025년 6월 급여). 행: 종별별(TM101~TM104) "공공교통_2km미만 / マイカー2km미만..." 컬럼: PV판정일수(15.0)/지급제 개시일·종료일·금액/算定額/出力額...
💭 요지: 단체 테스트 시연 — Csion으로 더미 유저 만들어 P3 화면에서 신청 → 결과 확인. Kenta가 핵심 질문 던짐: "화면 없이 백엔드만으로..."
🆕 새 용어: 継続支給(케이조쿠시큐) = 계속지급 확인 / 算定額/出力額 = 산정액/출력액 / 中間テーブル(추칸 테이블) = 지시 테이블...
```

문제점:
- 한 섹션에 한 줄이 수십 자 → 화면 wrap으로 여러 줄 됨
- `/` 와 `,` 로 여러 항목을 한 줄에 밀어넣음
- 들여쓰기/불릿 없음 → 계층 안 보임

```
✅ 좋은 예 (같은 내용, 불릿 분리):
📊 슬라이드
   • P3 "継続支給の確認" 테스트 환경
   • 종별(TM101~TM104) × 정기권 매트릭스

💭 요지
   • 단체 테스트 시연 — 더미 유저로 P3 신청
   • 핵심 질문(Kenta): "백엔드만으로 테스트 가능?"
   • 답(平手): 중간 테이블로 화면 우회 가능

🆕 새 용어 (top 3)
   • 継続支給 — 계속 지급 확인
   • 中間テーブル — Trans 진입점
   • 算定額/出力額 — 산정액 / 출력액
```

같은 정보량, 훨씬 빨리 읽힘.

### 효율 원칙

- **메인 세션에서 직접 처리** — 서브에이전트 호출 X (응답 속도 우선)
- 글로서리는 grep 수준으로만 참조 (전체 read X)
- 이전 발화 맥락은 마지막 100~200줄만 (notes.md 전체 read X)
- 분석에 필요 없는 호출은 하지 말 것

### 예시

**좋은 예 1** (이미지 + 텍스트, 정보 풍부):
```
📸 슬라이드 03 + 발화 (13:45)

📊 슬라이드
   • Calcu 9단계 급여 계산 흐름도
   • 사회보험료 계산은 3번째 단계

💭 요지
   • 발표자가 사회보험료 계산 위치를 설명
   • 앞 단계(지급액)의 결과가 입력으로 들어감

🆕 새 용어 (top 2)
   • 사회보험 Calculation — 사회보험료 계산 모듈
   • 過課税額 — 과세 금액
```

**좋은 예 2** (텍스트만, 번역 오류 집중):
```
📝 추가 → 슬라이드 03 (13:48)

💭 요지
   • Varit이 변동 데이터 입구임을 재차 강조

⚠️ 번역 오인
   • "발리섬" → Varit (バリット)
   • "예능 단계" → 계산 단계 (芸能↔計算 동음)
```

**좋은 예 3** (최소 — 새 정보 없음):

```
💭 요지
   • 앞 발화 부연, 새 정보 없음
```

**좋은 예 4** (이미지만, 텍스트 없음):

```
   • 조직도 — HR / Payroll / Dev 3부서
```

**나쁜 예** (긴 분석):

## 모드 1, 4 응답 길이

모드 1(새 미팅), 모드 4(context 저장)는 분석할 내용이 없으므로 **1~2줄**만:

- ✅ `📁 새 미팅 시작 — {경로}`
- ✅ `📋 context 저장됨`

## 엣지 케이스

| 상황 | 대처 |
|---|---|
| `/cap`만 보내고 이미지/텍스트 둘 다 없음 | `❓ 캡처할 이미지나 텍스트가 없습니다` |
| 활성 미팅 없는데 이미지 보냄 | 모드 2 1단계 안내 |
| 한 메시지에 이미지 여러 장 | 각각 다음 번호로 별도 슬라이드 저장 (텍스트는 마지막 슬라이드에만 붙임) |
| meeting-name에 공백/한글 | 슬러그화: 공백→하이픈, 한글은 그대로 유지 |
| `notes.md`가 없는데 모드 2/3 호출 | 활성 미팅 폴더가 손상된 상태. 알리고 중단 |
| 사용자가 애매한 문장 보냄 (context인지 발화인지) | 짧게 물어본다: "발화(텍스트)로 저장할까요, 배경(context)로 저장할까요?" |

## 주의

- 슬라이드 번호는 **반드시 디렉토리 스캔 기반**으로 매긴다
- `~/meetings/.current`는 단일 라인 파일
- macOS 한정: BSD `date`, 경로 구분자 `/`
- **이 스킬의 본질**: 저장 + 짧은 실시간 분석. 두 가지 모두 매번 수행한다.
- **무거운 작업은 위임**: 종합 분석(`meeting-review`), 누적 요약(`recap`), 명시적 질문(`ask`)은 다른 스킬의 책임. cap의 분석은 항상 짧고 빠르게.
