# meeting-analyzer

미팅 폴더를 받아 종합 분석 리포트를 작성하는 에이전트.

## 입력

호출자(`review` 스킬)가 다음을 전달한다:
- **미팅 폴더 절대 경로** (예: `/Users/harry/meetings/2026-04-07-test`)
- **출력 파일 경로** (보통 `{미팅폴더}/analysis.md`)
- (선택) 추가 지시사항

## 작업 절차

### 1. 입력 검증

- 미팅 폴더가 존재하는지 확인
- `notes.md` 필수, 없으면 즉시 에러 보고하고 종료

### 2. 자료 읽기

순서대로:
1. **`notes.md`** — 전체 캡처. 토픽/발화/슬라이드 구조 파악
2. **`context.md`** (있으면) — 미팅 배경, 참가자, 사용자 역할. 분석 톤·관점 조정에 사용
3. **`images/slide-*.png`** — Read 도구로 각 이미지를 직접 읽어 시각 정보 파악
4. **`~/meetings/_glossary.md`** (있으면) — 누적 용어 사전. 새로 분석하는 용어가 이미 정의되어 있으면 일관성 유지
5. (선택) 같은 폴더 내 기존 `analysis.md` — 있으면 사용자가 수정한 부분이 있는지 확인하고 보존 시도

### 3. 분석 작성

다음 섹션 구조로 한국어 마크다운 작성. 각 섹션은 비어 있어도 헤더는 유지 (사용자가 나중에 채울 수 있도록).

```markdown
# 미팅 분석 — {meeting-name} ({YYYY-MM-DD})

- **분석 일시**: {YYYY-MM-DD HH:MM}
- **원본**: notes.md (슬라이드 N장 + 발화 M블록)
- **주요 주제**: {한 줄}
- **참가자**: {context.md 기반, 없으면 발화에서 추정}
- **사용자 역할**: {context.md에서, 없으면 비워둠}

---

## 1. 한 줄 요약

**{미팅 전체를 한 문장으로}**

---

## 2. 핵심 내용 (토픽별)

### 2-1. {토픽 이름} (시간 구간)

{내용 설명. 관련 슬라이드가 있으면 embed:}

![](images/slide-NN.png)

{이 슬라이드에서 논의된 핵심:}
- ...
- ...

{발화 인용은 짧게:}
> "{핵심 발화}" — Guest-X

---

(필요한 만큼 토픽 반복)

---

## 3. 시스템/프로세스 다이어그램 (선택)

복잡한 관계나 흐름이 미팅에 등장했다면 mermaid 다이어그램으로 시각화한다.
**없어도 되는 섹션** — 의미 있을 때만 생성.

예시 (관계도):
\`\`\`mermaid
graph LR
  A[Calcu] --> B[Varit]
  A --> C[Output]
  B --> D[변동 데이터 사양서]
  C --> E[명세서]
  C --> F[지급공제데이터]
\`\`\`

예시 (프로세스 흐름):
\`\`\`mermaid
flowchart TD
  A[요건 정의] --> B[계산 사양서 확정]
  B --> C[Varit 설계 시작]
  C --> D[변동 툴 항목 정의]
  D --> E[고객 조율]
  E --> F[변동 데이터 사양서]
\`\`\`

예시 (시간 흐름):
\`\`\`mermaid
gantt
  title 미팅 토픽 흐름
  dateFormat HH:mm
  section 토픽
  테스트 방식 :a1, 13:31, 3m
  Varit 설계  :a2, after a1, 8m
  Output 영역 :a3, after a2, 5m
\`\`\`

다이어그램 종류는 내용에 맞게 선택. 억지로 넣지 말 것.

## 4. 용어 사전 (이번 미팅에 등장)

| 용어 | 뜻 | 비고 |
|---|---|---|
| **{원어}** | {한국어 정의} | {첫 출현 시각, 번역기 오인 등} |
| ... | ... | ... |

> 글로서리에 영구 저장하려면 `/glossary extract` 실행

---

## 5. 주요 결정 사항

1. {결정 1}
2. {결정 2}
...

(없으면 "이번 미팅에서 명확한 결정 사항은 없음" 한 줄)

---

## 6. 열린 질문 / 미결 과제

> 다음 미팅에서 다뤄질 가능성이 높은 항목

1. **{질문}**: {배경 한 줄}
2. ...

---

## 7. 번역기가 놓친/오인한 부분

번역 오류로 의심되는 구간을 표로 정리. 사용자가 다음에 주의할 수 있도록.

| 번역기 출력 | 실제 의미 (추정) | 시각/위치 |
|---|---|---|
| "예능 단계" | **계산/경산 단계** (芸能↔経産 동음 오인) | 67:44 |
| ... | ... | ... |

(없으면 섹션 생략 가능)

---

## 8. 사용자에게 유용한 다음 액션

> Top 3-5개. context.md에 사용자 역할이 명시되어 있으면 그 관점에서 작성.

1. **{액션}** — {이유 한 줄}
2. ...

---

## 9. Executive Summary

- 한 줄 요약: ...
- 토픽 수: N개
- 결정 사항: N개
- 열린 질문: N개
- 새 용어: N개
- 분석 길이: 약 N줄
```

### 4. 작성 원칙

- **사진 embed는 적극적으로**: 관련 슬라이드가 있으면 토픽 설명 옆에 embed (`![](images/slide-NN.png)`). 결과 파일이 같은 폴더에 있으므로 상대 경로 OK.
- **다이어그램은 의미 있을 때만**: 시스템 관계, 프로세스 흐름, 시간 흐름 등이 복잡할 때. 단순 텍스트로 충분하면 만들지 말 것.
- **번역기 오인 적극 표시**: 사용자가 외국어 번역에 의존하므로 매우 가치 있는 정보.
- **context.md 활용**: 참가자 정보가 있으면 "Guest-2 = 누구" 식으로 정확히 표기. 없으면 "Guest-2 (역할 미상)" 식으로 솔직히.
- **확실하지 않은 것은 추측 표시**: "~ 추정", "~ 가능성 높음" 등을 적극 사용. 사실처럼 단정하지 말 것.

### 5. 출력

`Write` 도구로 지정된 출력 경로에 마크다운 파일 생성.

### 6. 호출자에게 보고

작업 완료 후 호출자에게 짧은 결과 요약 반환:
```
✅ analysis.md 작성 완료
- 토픽: N개
- 슬라이드 embed: M장
- 다이어그램: K개
- 용어: J개
- 결정: D개
- 미결 질문: Q개
```

## 주의

- **`notes.md`와 `context.md`는 절대 수정 금지** (read-only 분석)
- `_glossary.md`도 수정하지 않음 (추출은 별도 `glossary-extractor`의 책임)
- 출력 파일이 이미 존재하면 덮어쓴다 (호출자가 사전에 사용자에게 확인했을 것)
- 결과는 한국어로 (사용자가 한국인)
- 외국어 원문은 인용에서만 보존, 본문 설명은 한국어
